========================================
COMPREHENSIVE TEST LOG SAMPLES
========================================

NOTES:
- Email verification folder configuration is stored in email_verification_config.json
  If folder names or locations change, update that file instead of editing code.
  See EMAIL_VERIFICATION_CONFIG_README.md for details.

- SharePoint list uses two text columns: "Dateandtime" (date) and "Time" (time).

- Email verification now:
  * Waits 10 seconds and retries if email not found initially
  * Search order on EVERY attempt (highest priority first):
      1. Inbox / Create CRM Case  (most specific staging folder)
      2. Inbox / Create CRM Case / Retry
      3. Inbox / Create CRM Case / Retry 2
      4. Origin-specific folder(s)  (e.g. Calls Entered, Emails From Franchisees)
      5. Main Inbox  (last resort)
  * ALL origins now verify the sender email address (check_sender=true for all)
  * If still not found, tries +/-1h (timezone/DST), +/-12h (AM/PM swap) and +/-24h (wrong date) offsets
  * If found at an offset, auto-corrects SharePoint (Dateandtime/Time) and CRM (received-on)
  * Updates SharePoint "EmailVerification" column (Yes/No) based on result
  * Runs for both new cases AND increment cases (but not duplicates)

- Email movement (NEW):
  * On SUCCESS (case created, increment, or duplicate): email is marked READ and moved to the correct
    origin folder. This fires whenever email verification returned a msg_id.
  * On INVALID STORE (all fallbacks exhausted): email is marked UNREAD and moved to main Inbox.
  * If email verification found no email (NOT FOUND), no movement occurs.
  * Destination folder is determined by Origin field + sender domain:
      Voice to Text / Phone  -> Inbox / Calls Entered
      Email (@winmarkcorporation.com) -> Inbox / Emails From FOMs
      Email (other domain)   -> Inbox / Emails From Franchisees
      Internal               -> Inbox / INTERNAL REQUESTS
      Splunk                 -> Inbox / INTERNAL REQUESTS / Splunk Alerts

KEY PATTERNS TO LOOK FOR:
========================================

1. NEW CASE CREATED:
   - "Case created for store {store}: {ticket_number}"
   - Followed by "Received On:", "Created On:", "Time Difference:"

2. INCREMENT (SAME-SUBJECT):
   - "Increment (same-subject): {ticket_number}"
   - "Increment note added to {ticket_number}"
   - Note: When multiple active cases share the same subject, the one matching the incoming case type is preferred.
     Falls back to the most recently created case if no case-type match is found.

3. INCREMENT (RESOLVED-SAME-DAY-SUBJECT):
   - "Increment (resolved-same-day-subject): {ticket_number}"
   - "Increment note added to {ticket_number}"
   - Note: Only reached if no active same-subject case exists (active cases always checked first).
   - Note: When multiple qualifying resolved cases share the same subject, the one matching the incoming case type is preferred.

3B. INCREMENT (LINKED-SUBJECT):
   - "Increment (linked-subject): {ticket_number}" - active case matched the other side of a subject link
   - "Increment (resolved-linked-subject): {ticket_number}" - resolved-today case matched the other side
   - Links defined in LINKED_SUBJECTS in sharepoint_poller.py (all bidirectional):
     * Inventory Issue (any type) <-> Question + Inventory
     * Appointment (any type) <-> Question (any type)
     * Appointment + POS <-> Hardware Issue + POS
     * Appointment + Server <-> Hardware Issue + Server
     * Appointment + Pole Display <-> Hardware Issue + Pole Display
     * Appointment + Internet/Firewall/CDE <-> Internet/Network Issue + Firewall
     * Appointment + Ingenico <-> Internet/Network Issue + CCT/CDE
     * Hardware Issue + POS <-> Internet/Network Issue + CCT/CDE
     * Hardware Issue + Cash Drawer <-> Printer + Receipt
     * Hardware Issue + POS <-> DRS Access Issue (any type)
     * Hardware Issue + Server <-> DRS Access Issue (any type)
     * Hardware Issue + POS <-> Software Issue + Software Update
     * Hardware Issue + Server <-> Software Issue + Software Update
     * Hardware Issue + POS <-> Software Issue + General DRS Issue
     * Hardware Issue + Server <-> Software Issue + General DRS Issue
     * DRS Access Issue (any type) <-> Software Issue + Software Update
     * DRS Access Issue (any type) <-> Software Issue + General DRS Issue
     * Hardware Issue + POS <-> Software Issue + Windows Issue
     * Winmark Connect + Issues <-> Reports Issue + Reg/Day/Month/Year
     * Winmark Connect + Questions <-> Reports Issue + Reg/Day/Month/Year
     * Winmark Connect + Issues <-> Reports Issue + Other
     * Winmark Connect + Questions <-> Reports Issue + Other
     * Internet/Network Issue (any type) <-> DRS Access Issue (any type)
     * Internet/Network Issue (any type) <-> Dayclose Issue (any type)
     * DRS Access Issue (any type) <-> Dayclose Issue (any type)
     * Reports Issue (any type) <-> Question + Report

4. DUPLICATE (WITHIN 1 MIN):
   - "Exact duplicate (duplicate (within 1 min)): {ticket_number}"
   - "Time comparison: new={time} existing={time} diff={diff}"

5. TIME WARNINGS:
   - "[TIME WARNING] Received-on time" - Future date
   - "[RED FLAG] Time Difference" - Negative or 8+ hours

6. EMAIL VERIFICATION:
   - "[OK] Found email in '{folder}' at {time} from {email}" - Success (immediate)
   - "[OK] Found email in 'Inbox/Create CRM Case' at {time} from {email}" - Found in staging folder
   - "[OK] Found email in 'Inbox/Create CRM Case/Retry' at {time} from {email}" - Found in Retry subfolder
   - "[OK] Found email in 'Inbox/Create CRM Case/Retry 2' at {time} from {email}" - Found in Retry 2 subfolder
   - "Email not found on first check. Waiting 10 seconds" - Retry initiated
   - "Retrying email search in ['Create CRM Case', 'Create CRM Case/Retry', 'Create CRM Case/Retry 2', {folders}]" - Second attempt
   - "[NOT FOUND] No email found in {origin_folders} ... or +/-1h/12h/24h offsets" - Not found after all attempts
   - "Expected sender: {email}" - ALL origins now show this when email is not found (check_sender=true for all)
   - Note: Search priority on every attempt: Inbox/Create CRM Case -> Retry -> Retry 2 -> origin folder(s) -> Inbox
   - Note: Retry/Retry 2 subfolders are used by folder_monitor.py to stage emails awaiting Copilot retry

6b. EMAIL MOVEMENT (on successful processing):
   - "[Email] Marking verified email as read and moving to correct folder." - always logged before move
   - "[Email] Marked as read and moved to 'Inbox / {folder}'." - confirms destination
   - NOTE: Only fires when email verification found and returned a msg_id.
   - NOTE: On error (invalid store, validation/CRM failure): email is moved to Inbox UNREAD instead.
   - NOTE: No email movement when email verification returned NOT FOUND.
   - NOTE: "[Email] Failed to reroute email to 'Inbox / ...': {error}" (WARNING) if move fails.

7. TIME-CORRECTED EMAIL VERIFICATION (runs BEFORE case creation):
   - "Trying time-corrected search (+/-1h, +/-12h, +/-24h)..." - Offset search initiated
   - Offsets tried in order: -1h, +1h, -12h, +12h, -24h, +24h
   - "+/-1h (timezone/DST error)" - AI off by 1 hour (e.g. CDT vs CST confusion)
   - "+/-12h (AM/PM swap)" - AI entered wrong AM/PM
   - "+/-24h (wrong date)" - AI entered wrong date
   - "[OK] Found email with {offset} correction in '{folder}'" - Found at offset
   - "Correcting received time from {old} to {new}" - Time correction applied
   - "[Time Correction] Corrected received_on to {local} (UTC: {iso})" - received_on fixed
   - "[Time Correction] Updated SharePoint: Dateandtime={date}, Time={time}" - SharePoint updated
   - "[NOT FOUND] No email found in ... or +/-1h/12h/24h offsets" - All offsets exhausted
   - Case is then created with the corrected time (no post-creation CRM update needed)

8. DRAFT REPLY:
   - "Found draft: '{subject}' -> moving to {mailbox} Drafts" - Draft found, proceeding to move
   - "Draft moved successfully (new ID: ...)" - Move completed
   - "Draft not found (attempt X/7, searched N draft(s)). Waiting 10s before retry..." - Retry in progress
   - "Retrying draft search for '{email}'..." - Between retries (up to 6 retries, 60s max)
   - "No draft found in {mailbox} addressed to '{email}' after 7 attempts (60s). Searched N draft(s) on final attempt." - All retries exhausted

9. VALIDATION ERRORS (bad subject / case type):
   - "Validation error for item {id} (store {store}): {reason}"
   - "Item {id} marked as Failed: {reason}"

9b. INVALID STORE NUMBER (store not in CRM) — phone fallback attempted:
   - "Store '{store}' not found/inactive. Attempting phone fallback with: {phone}" - fallback triggered
   - "Phone fallback: no CRM account found for {phone}." - phone also found nothing
   - "Invalid store number for item {id} (store {store}): No account found for store number '{store}'. Phone fallback also found no match for {phone}."
   - "Item {id} marked as Invalid Store Number: ..."
   - "[Email] Moving verified email back to Inbox and marking unread..."
   - "[Email] Moved email to Inbox."
   - "[Email] Marked email as unread."
   - NOTE: If contact_phone is blank, the phone fallback lines are skipped and error goes straight to Invalid Store Number.

9c. INVALID STORE NUMBER (store inactive/closed in CRM) — phone fallback attempted:
   - Same phone fallback lines as 9b, then:
   - "Invalid store number for item {id} (store {store}): Account for store number '{store}' is inactive/closed. Phone fallback also found no match for {phone}."
   - NOTE: The key distinction in the original error remains:
       * Never existed  -> "No account found for store number '{store}'."
       * Inactive/closed -> "Account for store number '{store}' is inactive/closed."

9d. PHONE FALLBACK — SUCCESS (wrong store number corrected via phone):
   - "Store '{wrong}' not found/inactive. Attempting phone fallback with: {phone}"
   - "Phone fallback matched: store {correct} ({name}) via phone {phone}. Correcting store number from '{wrong}' to '{correct}'."
   - "[Store Correction] Updated SharePoint Storenumber from '{wrong}' to '{correct}'."
   - "Found account: {name} (store {correct})" — duplicate checks then run with corrected store
   - After Processed: standard email movement applies (see pattern 6b above).
   - NOTE: If SharePoint store update fails: "[Store Correction] Could not update SharePoint Storenumber: {error}" (WARNING)

9e. PHONE FALLBACK — AMBIGUOUS (multiple CRM accounts match):
   - "Store '{store}' not found/inactive. Attempting phone fallback with: {phone}"
   - "Phone fallback ambiguous: Phone '{phone}' matched {N} accounts: store {s1} ({n1}), store {s2} ({n2}). Cannot determine correct account." (WARNING)
   - "Invalid store number for item {id} (store {store}): ... Phone fallback was ambiguous: ..."
   - Same email-to-Inbox flow as 9b above.

10b. CRM CONNECTIVITY RETRIES (transient server errors):
   - "[CRM] Network error on attempt {X}/3, retrying in 10s: {error}" (WARNING) - connect timeout or connection reset
   - "[CRM] Server error {5xx} on attempt {X}/3, retrying in 10s..." (WARNING) - CRM returned 5xx
   - 3 attempts total, 10 seconds apart; covers ConnectTimeoutError, ReadTimeout, ConnectionResetError
   - If retries succeed: processing continues normally (no Failed status, no email move)
   - If all 3 fail: raises to outer handler -> "Failed to process item {id} (store {store}): {error}" (ERROR)
     then email returned to Inbox unread and item marked Failed (requires manual re-approval)

10. STATUS UPDATES:
    - "Item {id} status updated to 'Processing'"
    - "Item {id} status updated to 'Processed'"

11. SUMMARY:
    - "Done. Processed {count} item(s)."
    - "No approved items to process."

   - "Mailbox  : {mailbox}"
   - "Source   : Inbox / INTERNAL REQUESTS / Splunk Alerts / CF and Non-Start Point"
   - "CF Late  → Internal Requests  (case type: CF Late, contact: Internal)"
   - "Non-Start → Splunk Alerts      (case type: Non-Start Point, contact: Splunk)"
   - "Interval : {N}s ({N} min)"
   - Optional prefix: "Loaded state: {N} processed ID(s)."

2. EMAIL DETECTION:
   - "Found {N} message(s) in folder." - Messages present
   - "No messages in folder." - Empty source folder
   - "Processing '{subject}' (type={cf_late|non_start_point})" - Processing begins
   - "Skipping unrecognised subject: '{subject}'" - Unknown email type, not processed

3. CF LATE - PARSING AND CASE CREATION:
   - "Found {N} store(s) in CF Late report." - Parsed store count
   - "No store entries parsed — check email body format." - WARNING, parsing failed
   - "Store {store}: {N} day(s) late — below threshold, skipping." - days_late < 3, skipped
   - "Store {store}: duplicate {ticket} — skipping." - Active case today, skipped
   - "Store {store}: created {ticket} (ID: {guid})" - Case created successfully
   - "Store {store}: account error — No account found for store number '{store}'." - Store not in CRM
   - "Store {store}: failed to create case — {error}" - CRM API error
   - "Email moved to Internal Requests." - Normal move after processing
   - "Email moved to Create CRM Case (fallback)." - Fallback when any store creation fails

4. NON-START POINT - PARSING AND CASE CREATION:
   - "Found {N} store(s) in Non-Start Point alert." - Parsed store count
   - "No store entries parsed — check email body format." - WARNING, parsing failed
   - "Store {store}: duplicate {ticket} — skipping." - Active case today, skipped
   - "Store {store}: created {ticket} (ID: {guid})" - Case created successfully
   - "Store {store}: account error — No account found for store number '{store}'." - Store not in CRM
   - "Store {store}: failed to create case — {error}" - CRM API error
   - "Email moved to Splunk Alerts." - Normal move after processing
   - "Email moved to Create CRM Case (fallback)." - Fallback when any store creation fails

5. TEST_MODE:
   - "TEST_MODE: {ticket} cancelled." - Case created then immediately cancelled (TEST_MODE=True)
   - Description in CRM is prefixed "test - " when TEST_MODE=True
   - Normal "Store {store}: created {ticket}" log still appears after the cancel line

6. ALREADY PROCESSED:
   - "Already processed: '{subject}' — skipping." - Email's internetMessageId in state file

7. CYCLE SUMMARY:
   - "Total cases created this cycle: {N}" - Logged only when N > 0
   - "Sleeping {N}s until next check..." - End of every cycle

8. ERRORS:
   - "Folder '{name}' not found under current path." - Sub-folder missing during path walk
   - "Source folder not found. Retrying next cycle." - Fatal path failure, cycle skipped
   - "Destination folder(s) not found. Retrying next cycle." - CF Late or Non-Start dest missing
   - "'Create CRM Case' folder not found — fallback disabled." - WARNING, fallback unavailable
   - "Could not fetch body: {error}" - Failed to retrieve email body; email skipped entirely
   - "Unexpected error in poller cycle: HTTPSConnectionPool..." - Network timeout, cycle aborted
   - "Unexpected error in poller cycle: {error}" - Any unhandled exception in a cycle
